# BARAQ — Production Transport Security (TLS)



**Document:** Enforcing HTTPS for commercial deployments

**Applies to:** the packaged console (BARAQ.exe) and agent intake



---



## 1. Why this matters



The console serves both the web UI and the agent intake channel (HTTPS on

port 8443). In production, all traffic must be encrypted and the server must

prove its identity with a certificate the clients already trust. Running

plain HTTP or with a self-signed certificate is acceptable only in the

development laboratory.



## 2. What the product enforces



- `BARAQ_ENV=production` sets `IS_PRODUCTION` in the backend.

- **Startup gate**: in production the server refuses to boot when TLS is

  disabled (`BARAQ_TLS=1` required). The only override is

  `BARAQ_ALLOW_PLAINTEXT_PROD=1` — documented for emergencies, never for

  permanent operation.

- The session cookie is forced to `Secure` whenever TLS is enabled.

- First-run credentials are generated randomly per installation and written
  to `first_run_credentials.txt` next to the executable (the password is also
  stored in the DPAPI vault). The bootstrap account carries
  `must_change_password`, so the console blocks all other endpoints until the
  operator changes the password; the handoff file is then deleted
  automatically.



## 3. Choosing a certificate



| Scenario | Recommended |

|---|---|

| LAN deployment, no public domain | Internal CA (e.g. Windows AD CS) or a self-signed cert with SANs for every agent-facing address; distribute the CA/root to the agents |

| Public domain (e.g. soc.example.com) | Public CA (Let's Encrypt via certbot, or a commercial CA) — agents and browsers trust it automatically |

| Large fleet | Consider mTLS / per-agent client certificates (future work; today agents authenticate with the agent key header over TLS) |



## 4. Provisioning (current tooling)



Development certificates are generated by `scripts/gen_cert.ps1` into

`certs\baraq.crt` / `certs\baraq.key` (self-signed, SANs: localhost,

127.0.0.1, LAN addresses). For production:



1. Obtain a certificate for the console hostname(s).

2. Place the PEM certificate and private key where the server can read them.

3. Configure:



```

BARAQ_TLS=1

BARAQ_TLS_CERT=C:\path\server.crt

BARAQ_TLS_KEY=C:\path\server.key

BARAQ_ENV=production

```

### The server enforces this now, it does not just record it

`BARAQ_TLS=1` used to be stored in the configuration and then ignored by the
launcher: the API bound plain HTTP while the `Secure` cookie flag was set and
the service reported itself healthy and "encrypted". That is fixed. The
launcher reads `BARAQ_TLS_CERT`/`BARAQ_TLS_KEY`, serves real HTTPS, and
**exits with an error** if TLS is requested but the certificate or key is
missing or unreadable. It prints the scheme on startup, so confirm it from the
log:

```
BARAQ backend starting on https://0.0.0.0:8443
```

If you start the API yourself instead of via the launcher, you own the
certificate:

```
python -m uvicorn backend.main:app --host 0.0.0.0 --port 8443 --ssl-certfile C:\path\server.crt --ssl-keyfile C:\path\server.key
```

Agents pin the server certificate with `-TlsCert` (see
`docs/agent-deployment.md`); they refuse to talk to a different certificate.



4. Restart the console and verify:

   - `https://<host>:8443/api/system/status` returns the status JSON.

   - `BARAQ_ENV=production` and TLS disabled aborts startup with the clear

     gate message.



## 5. Verification checklist (pre-sale)



- [ ] Certificate chain completes to a CA the agents/browsers trust

- [ ] No hostname/IP that agents use is missing from the certificate SANs

- [ ] TLS version and ciphers reviewed (TLS 1.2+; disable TLS 1.0/1.1)

- [ ] Production boot gate tested: `BARAQ_ENV=production` without TLS fails

- [ ] Default credentials cannot survive first login

- [ ] Session cookies marked Secure when TLS is on

- [ ] Agent enrollment uses the TLS-pinned server certificate
